Purpose

The Enterprise Bedrock Base System Message is the foundational behavioral contract for every AI agent on the enterprise AI platform. As organizations grow from single use cases to a portfolio of agents, independently written prompts lead to inconsistent behavior, uneven quality, duplicated logic, governance gaps and rising maintenance effort.

This template standardizes how agents reason, consume context, weigh evidence, handle uncertainty, communicate confidence, resist injection, protect data and escalate to people. It carries no business logic. Domain behavior is added through Agent Instructions layered on top, never by editing the enterprise standard.

It is shared across Requirements Analysis, Test Design, Test Case Generation, Test Automation, Validation, Defect Analysis, RCA, Review and Workflow agents.

How the message is layered

Order is a cost and safety decision. Content that never changes sits first so Bedrock prompt caching can reuse it. Content that changes per request sits last and can never leak upward.

1. Shared enterprise base LockedGovernance, evidence, injection defense, tools, privacy, security. Identical for every agent.
optional checkpoint 1 · shared across agents
2. Agent layer EditableRole, objective, Agent Instructions, reasoning steps, output fields. Identical for every call of one agent.
cachePoint 2 · static prefix ends
3. Session context DynamicDate, tenant, user role, permissions, workflow and step. Changes on every request.

Customization guidance

Specialize through the agent layer. The shared base is a governance control, so it stays identical across the portfolio.

Sections that can be modified

    Sections that must not be modified

      Why: locked sections carry enterprise governance, Responsible AI controls, traceability, security standards, injection defense, privacy rules and RAG grounding. Changes require approval from the AI Architecture and Governance teams.

      Precedence rule

      If Agent Instructions conflict with the shared base, the base wins. Agent Instructions may narrow behavior (tighter scope, stricter approvals) and may never widen it.

      Agent teams may

      • Set role, objective, in-scope and out-of-scope tasks.
      • List tools, triggers and approval rules.
      • Add domain rules and a source authority rule.
      • Add reasoning steps and agent-specific output fields.

      Agent teams may not

      • Remove or rename base output fields (status, confidence, evidence_refs, flags).
      • Allow data access beyond session permissions.
      • Disable escalation, injection or security rules.
      • Switch on general model knowledge without labeling it.

      Change approval workflow

      1. Propose. State the change, the section, and the behavior it should alter.
      2. Evaluate. Run the golden set and the red-team set. Compare against the current version.
      3. Review. AI Architecture and Governance approve any locked-section change. Agent-layer changes need the agent owner and a peer.
      4. Version. Bump the semantic version and update the change log.
      5. Release. Canary rollout with one-step rollback.
      6. Monitor. Track schema failures, escalation rate, guardrail hits, cache hit ratio and cost.

      Release and controls

      A system message is a soft control. These controls make the behavior it describes enforceable and measurable.
